# 结构化解构层（decomp.md）方法论

> **读者**：test-case-design agent **阶段1**（解构）必读；阶段2（生成）只需读 confirmed 的 `decomp.md`。
> **前置**：`artifacts/README.md`、`artifacts/agents/test-case-design.md`。

## 为什么有这一层

旧链路是 `需求 → cases.md`。这一步跨度太大，导致三个病：

1. **覆盖度不可审**——用例多不等于覆盖全，用户只能凭感觉看"够不够"，而"够不够"恰恰是他唯一
   无法验证的东西。
2. **缺口是隐形的**——需求没写的（空值行为、非法状态迁移、影响面）在 cases.md 里表现为"没有这
   条用例"，而**缺席不会引起注意**。
3. **不积累**——每次从零读需求，上个迭代实测到的结论没有承接位。

解构层把这一跳拆成两跳：

```
需求/设计图/线上UI  ──阶段1(解构)──►  decomp.md 7 张固定结构的表  ──GATE 0──►  确认
                                              │
                                     阶段2(生成) = 机械映射
                                              ▼
                                    cases.md + flow.md ──GATE 1──►
```

- **解构是有判断的、可评审的**：每个 cell 带「来源 + 置信度」，缺口从"没有用例"变成"表里一个
  显式的 ⚠️ 行"。缺席变成在场。
- **生成是机械的**：表 × 方法 → 用例，有固定映射和数量下界（见下「生成映射」）。用例数量不再
  是 agent 的自由裁量。
- **覆盖率有定义**：`覆盖缺口 = 7 张表里 ⚠️ 和空白 cell 的总数`；另有
  `控件覆盖率 = 表⑦ 覆盖的 page_ref 数 ÷ 地图该页 elements 总数`。方法论的全部工作就是逐迭代把
  这些洞填掉——而不是"再想想还有什么用例"。

## 一、7 张表（固定结构，不许增删列）

所有表共享两个尾列：

| 列 | 取值 | 说明 |
|---|---|---|
| **来源** | `需求` / `设计图` / `page_map` / `知识库` / `已有用例` / `实测` / `用户` / `类比` / `无` | 这个 cell 的证据出处，具体到文件/章节/图名。**引用写成可定位的格式**：需求章节 `需求 §2.2`、变更日志 `变更日志 2026-09-28`、设计图 `设计图 img_04` —— 评审控制台按这三种格式把原文段落 / 变更行 / 图片直接贴到决策卡上，写成别的说法评审人就看不到原文 |
| **置信度** | `✅确定` / `🔶推断` / `⚠️缺失` | 见下「置信度判定」 |

> 「需求」泛指 PRD、需求描述、变更单、用户故事——具体是哪种，由下面的 A/B/C 档位区分。

### 权威源分工：什么听需求文档，什么听设计图（硬规矩）

**没有"以图为准"这种笼统说法。按信息类型分**：

| 信息类型 | 权威源 | 例子 |
|---|---|---|
| **规则类** | **需求文档说了算** | 必填/选填、**默认值**、取值范围与边界、校验规则、枚举取值集合、权限、状态流转、业务逻辑、计算公式 |
| **表现类** | **设计图说了算** | 文案字面值、控件形态（下拉/单选/开关）、布局与分组、导航层级、tab 顺序与命名、弹窗结构、按钮位置与数量、列表列顺序 |

**为什么规则类不能听图**：设计稿里的具体值几乎都是**示意数据**——设计师要让 mockup 看起来
完整，会随手填一个人名、选中一个下拉项。把它当规格会直接读出假规则。
> 例如：某论坛的"发帖"设计稿里，`标签` 下拉显示默认选中了 `问答`、`可见范围` 显示已勾选
> `公开`，而需求文档写的是"两个字段均选填，用户不选则为空、不公开"。按旧的"以图为准"会把
> "默认选中问答/公开"写成规格——错。下拉里那个碰巧被选中的值只是示意态，**规则类一律回到
> 需求文档。**

#### 关键区分：示意数据 vs 规格性表现

设计图上的东西不是铁板一块。同样是"图上的具体值"，两者性质完全不同：

| | 判别 | 例子 | 怎么处理 |
|---|---|---|---|
| **示意数据** | 设计师为了让 mockup 看起来完整**随手填的**，换成别的值不影响设计表达 | 人名、示例金额、某个下拉**碰巧选中**了一项、列表里的假数据行 | 忽略，**按需求文档填，不标冲突** |
| **规格性表现** | 设计师**特意画上去主张一条规则的**，改了值设计就变了意思 | 字符计数器 `0/1000`、必填星号 `*`、置灰/disabled 态、按钮的有无、Tooltip 里陈述的规则文字、枚举下拉**展开后的完整选项列表** | **算真冲突** → 标 `⚠️冲突` + 解构债，GATE 0 裁决 |

> 示意的一侧：搜索框设计稿里预填了"appium"当占位文字、结果列表画了 3 条假数据，都是纯示意，
> 按需求文档填即可，不标冲突。
> 规格性的一侧：搜索框旁的字符计数器、"最多输入 50 字"的提示文案、按钮的置灰态——设计师
> 不会随手画这些。

**判据一句话**：问"设计师是想说明这里长什么样，还是想规定这里能填什么"。后者就是规格性表现。
拿不准时**按规格性处理**（标冲突交人裁决）——多问一句的成本远低于抹平一个真分歧。

#### 报冲突前必须做「同一性核验」

判定"设计图与需求文档冲突"之前，**先确认两边说的是同一个对象**。这一步不做，最常见的产物就是
**假冲突**——两个长得像的字段被当成一个，然后浪费一次 GATE 0 裁决。

核验三问：① 是同一个**字段**吗（不是同名、不是同类）？② 在同一个**页面/弹窗**里吗？
③ 触发路径是同一条吗？三问有任何一个答不上来，标 `⚠️待核实` 而不是 `⚠️冲突`。

> 例如：批次 A 报了一条"真冲突"——需求文档说"删除话题"确认框的原因输入框上限 500 字，
> 设计图里的计数器却是 `0/1000`。复核发现：**`0/1000` 属于"举报话题"弹窗（需求文档对它
> 根本没写上界），`500` 属于"删除话题"弹窗（设计图里压根没画这一屏）**——两个不同字段，
> 不构成冲突。差点让人在 GATE 0 上裁决一个不存在的分歧。**"两处数字不一样"不等于冲突，
> 得先证明是同一处。**

**冲突处理**：
- **规则类冲突** → 先分是示意数据还是规格性表现（见上表）。示意数据 → 按需求文档填、不标冲突；
  规格性表现 → 标 `⚠️冲突` + 解构债交 GATE 0。
- 图上出现**需求文档明确排除的东西**（需求说枚举只有 A/B，图上出现 C；需求说该字段不存在，
  图上有）→ 一律真冲突，标 `⚠️冲突` + 解构债。
- **需求要求的东西设计图里没有**（需求说用户能删除自己的回复，回复卡片却没有任何删除入口）→
  **这是最贵的一类冲突**，标 `⚠️缺帧` + 解构债，因为它意味着功能可能压根没设计。
- **表现类冲突** → 按设计图填表，并在「来源」列写明 `设计图(与需求文字不一致)`。
- **图上有、需求文档完全没提的字段/控件** → 照录，标 `⚠️缺失`（需求侧无规则）+ 解构债，
  **不许因为"需求没写"就当它不存在**。

### 置信度判定（硬规矩）

- `✅确定` —— 需求文档/设计图/知识库 **明文写了**，或**实测取证过**，或用户在 GATE 0 答复过。
- `🔶推断` —— 无明文，但有**可指名的类比依据**（项目内同类字段/同类流程/平台默认约定）。
  **推断行必须在「来源」列写清类比对象**，如 `类比: page_map/testerhome/search.yaml 同类过滤字段`。
  没有类比对象的猜测不叫推断，叫编造 → 一律降级为 `⚠️缺失`。
- `⚠️缺失` —— 不知道。**保留该行、留空取值**，不许删行让表看起来干净。

> 红线：**宁可一整张表全是 ⚠️，不许编一个 ✅。** 解构层的价值全在诚实标注上——一个假 ✅ 会
> 让用户在 GATE 0 划过去，然后活到跑批阶段才炸。

### 审阅层级判定（硬规矩）

置信度标记回答的是"这个 cell 有多可信"，**它不回答"现在要不要打扰用户"**。少了后一个维度，
GATE 0 会把每一个 `🔶`/`⚠️` 无差别塞给用户——一个几百字的小需求就能堆出几十张待决卡，
而其中大半是"提测时看一眼就知道"的实现细节（下拉能不能搜索、元素是隐藏还是移出 DOM、
报错文案的精确措辞）。用户的注意力是这条链路上最稀缺的资源，**必须只花在他能答、且只有他能答
的问题上**。

**这个分类必须由写这行的你来做，不能交给下游过滤器**：你知道这行为什么不确定，
下游按关键词猜——猜不是懂。

**判据只有一句话**：这行问的是**「它现在长什么样 / 怎么实现的」**，还是
**「它应该长什么样 / 这条测试场景存不存在」**？

- 前者 → 观测/实测就能拿到答案，用户现在不用管，标 `可提测`
- 后者 → 答案是产品意图或测试范围，只有用户能定，标 `需判断`

**标法**：`⚠️冲突` 恒为 `需判断`，`⚠️待核实`（现状与需求文档不符）恒为 `可提测`，
**这两类不用额外标注，kind 本身已经决定**。只有 `🔶推断` 和 `⚠️缺失`（不含冲突/待核实）
两类必须在同一个 cell 里、紧跟置信度标记后面加方括号标签：

```
🔶推断［需判断］   或   🔶推断［可提测］
⚠️缺失［需判断］   或   ⚠️缺失［可提测］
```

几个例子对照着记：

| 写法 | 判断 | 为什么 |
|---|---|---|
| `🔶推断［可提测］角色下拉是否支持搜索` | 可提测 | 建完页面点一下就知道，猜错了改一个字段类型 |
| `⚠️缺失［需判断］提交时被隐藏的字段存不存库` | 需判断 | 落库即脏数据，且这是"该怎样"不是"现在怎样" |
| `🔶推断［可提测］校验失败的提示文案精确措辞` | 可提测 | 提测时截图一看就有了 |
| `⚠️缺失［需判断］存量成员会不会被新加的必填项卡住，连原本能做的操作都做不了` | 需判断 | 发版即故障级，答案不能等出了事故才知道 |
| `⚠️缺失［需判断］能否回退到上一步（界面里根本没有「上一步」按钮）` | 需判断 | 决定这整类测试场景存不存在，是范围问题不是细节问题 |

**不标就是没写完**：`🔶`/`⚠️` 缺了这个标签，跟缺了置信度本身一样，都是解构没做完。

### ① 功能点清单（骨架：定范围 + 优先级）

| ID | 功能点 | 类型 | 涉及角色 | 入口页面 | 来源 | 置信度 |
|---|---|---|---|---|---|---|

- `类型` ∈ `增` / `删` / `改` / `查` / `流程` / `配置` / `权限`
- `涉及角色` 按项目实际角色填（如 `游客` / `登录用户` / `管理员`，多角色写全，跨角色的功能点
  后面会长出越权用例）
- `入口页面` 必须能对上 `page_map` 里的页面；对不上就是 `⚠️缺失` + 后续派 page-map-sync
- **粒度**：一个功能点 ≈ 用户能独立说出口的一件事（"按关键词搜索话题"），不是一个按钮

### ② 字段规格表（覆盖率主战场 → 等价类 + 边界值）

| 字段 | 所属功能点 | 控件类型 | 必填 | 取值/约束 | 默认值 | 校验规则/报错文案 | 来源 | 置信度 |
|---|---|---|---|---|---|---|---|---|

- `控件类型` 用项目数据驱动层的 type 词汇（如 `text`/`dropdown`/`select`/`date`/`file`…），
  这样阶段2 能直接生成测试数据
- `取值/约束` 写 min/max/长度/格式/枚举值（枚举值抄**字面值**）
- `校验规则/报错文案` 抄字面值；需求文档不写报错文案是常态 → `⚠️缺失`
- **这张表最长，也最出 bug。** 每个字段至少要问全 7 件事，问不出的就是 ⚠️ 行：
  必填？空值怎样？长度上下界？格式约束？枚举有哪些？默认值？和别的字段有依赖吗？

### ③ 状态机（→ 状态转换法）

| 实体 | 当前状态 | 可流转到 | 触发动作 | 触发角色 | 前置条件 | 来源 | 置信度 |
|---|---|---|---|---|---|---|---|

- **必须画成 N×N 全矩阵**，不许只抄需求文档列的那几条合法迁移。做法：先枚举实体的全部
  状态（n 个），构造 n×n 格子，然后**逐格推导，不是逐格抄**：
  1. 需求明确写了的 → `✅合法` / `🚫禁止`，来源写章节号
  2. 需求没写、但能从**业务流程 + 界面证据**推出来的 → 自己推，给**带依据的**结论：
     `✅合法`（写触发动作 + 角色）或 `🚫禁止`（写依据：终态不可再迁移 / 该状态下没有入口 /
     按钮置灰或不存在 / 撤回只对"待审"有意义……），来源写 `推导：<出处> + <一句推理>`。
     置信度按依据强弱定：依据是需求文档的流程段、设计图的按钮态、实测的可点动作这类**明文证据**
     → `✅确定`（不进待审队列）；依据只是同类功能类比 → `🔶推断`，照常打［需判断］/［可提测］
  3. 只有**真正两可、不同实现都说得通**的格子才留 `⚠️未定义`，并且**必须写明为什么推不出**
- 判断标准：**一个熟悉业务的人看一眼就能答的格子，agent 必须自己答。** 需求文档没有画状态机，
  不等于状态机未定义——审批、撤回、取消、删除这些流程段落里，迁移规则大多已经隐含了。
  机械地把没明写的格子全标 `⚠️未定义`，会产出一大片噪声，淹没真正的缺口，评审人也会认为
  你根本没读懂需求。
- 留下来的 `⚠️未定义` 才是这套方法论最高产的 bug 矿：产品默认"没人会这么干"，代码里往往真没拦。
  GATE 0 要用户逐个确认「未定义 = 应禁止」还是「未定义 = 其实允许」。
- 跨角色格子单独看：`管理员能做 / 普通用户不能做` 的迁移 → 长出越权用例。

### ④ 业务规则表（→ 决策表）

| 规则ID | 条件 | 结果/约束 | 涉及字段 | 来源 | 置信度 |
|---|---|---|---|---|---|

- 从需求文档的「限制 / 约束 / 规则 / 注意」段落**逐句**抽，一句一行，不合并
- 条件与结果必须拆开写（`条件: 话题被举报次数 ≥ 3` / `结果: 话题自动隐藏待审核`）
- 多条件规则在这里保持原样，判定表化简放到阶段2 做
- **只写判定，不写呈现**：「置灰」「Hover 文案」「按钮隐藏」一律归表⑦，本表只留
  "不允许删除 / 硬拦截不许提交 / 值怎么算"。表⑦ 用 `规则回指` 指回本表行 ID。
  （判定的权威源是需求文档，文案字面值的权威源是设计图；两者混在同一个「结果/约束」cell 里，
  「来源」列必然错标一半——一行只能填一个来源。）

#### 必做扫描：锁定守卫 → 存量数据语义

**触发源＝表⑦**：表⑦ 里每一行 `状态 = ⊘置灰`（以及任何"有 X 时不可编辑"的呈现），
都要在表④ 追加**两行**——**呈现在⑦，但"锁能不能解、解了历史数据算什么"是判定，归④**：

| 追加行 | 问什么 |
|---|---|
| **锁释放路径** | 什么条件下这个锁会解开或绕开？（关联数据全部删除？进入终态？某个配置分支下守卫根本不成立？） |
| **存量数据语义** | 锁解开后改了值，**用旧值产生的存量数据**怎么办？重算 / 保持原值 / 混显 / 报错？ |

**为什么必须专门扫这一遍**：表②/表③ 的结构只逼你回答「这个字段现在能不能改」，不逼你回答
「改了之后历史数据算什么」——这是两个问题，而需求文档几乎从不写第二个。例如：
- "话题分类"字段规则是"有回复后被锁"，但如果判定口径从"有回复"松动成"有精华回复"，锁就会
  部分释放 → 那些按旧分类被索引的历史话题怎么显示？无人问。
- "每日发帖上限"字段规则是"进阶用户才解锁"，而**新注册用户永远不是进阶用户 → 该字段对新用户
  永远锁死**，可历史发帖记录是按旧上限校验生成的——**守卫在某个用户分层分支下整个失效**。

第二例尤其说明问题：光看"这个字段有锁"就放心了，等于漏掉一整条分支。扫描时对每个守卫都要问
一句「**有没有哪条配置分支让这个守卫不成立**」。

### ⑤ 操作旅程（→ 场景法，即 flow.md 的原料）

| 旅程 | 角色 | 入口路径（字面值） | 步骤 | 预期（字面值） | ⚠️待实测项 | 来源 | 置信度 |
|---|---|---|---|---|---|---|---|

- **入口路径必须查 `page_map` 的 entry 字段**——存量入口是已付过学费的坑（新功能设计图假设
  从首页顶栏进入，实际入口在某个二级菜单里）。查不到就标 `🔶推断`，让用户在 GATE 0 一眼纠正。
- 文案一律**字面值**，禁止意译。
- 步骤间的连接（"点 A 之后出现 B"）凡是从需求文字/画布排布/文件名编号推断而非图内直接证据
  （step 指示器、弹窗叠加）得出的，标 `🔶推断`。**推断可以有，隐藏的推断不可以有。**

### ⑥ 影响面（→ 回归 / 兼容性）

| 新功能点 | 关联已有模块 | 关联类型 | 回归风险 | 证据 | 来源 | 置信度 |
|---|---|---|---|---|---|---|

- `关联类型` ∈ `依赖`（新功能用了旧模块）/ `冲突`（改了旧模块行为）/ `复用`（共用组件/页面）
- `证据` 必须是**可点开的路径**：知识库文件路径 / `tests/test_xxx.py::test_yyy`
- **需求文档从不写影响面**，这张表 100% 靠自己挖。挖法（四条线）：
  1. **同页面**：新功能落在哪个 page_map 页 → grep 该页已有用例
  2. **同实体**：碰了哪个业务实体（如论坛的 topic / reply / user）→ grep 知识库与已有用例
  3. **同状态机**：改了表③ 哪个实体的状态 → 该实体全部存量流程都要看
  4. **同屏共现**（有设计图时必做）：新字段所在的**那一屏上还有哪些存量字段**？逐个问
     「它和新功能是什么关系——重复？冲突？该联动却没联动？」
     > 例如：新增的"话题置顶"开关落在"发帖设置"这一屏，**同屏就有存量字段"话题分类"**。
     > 如果置顶话题不受分类筛选影响，那分类筛选和置顶是什么关系？两者会不会同时生效导致
     > 列表排序冲突？需求文档没写，前三条 grep 线也挖不到——因为它既不同实体、也不同状态机，
     > **只是恰好在同一屏上**。这条线只有拿到设计图/实际页面才能走，纯文本需求必然漏。
- 用户是这张表最好的补全者（他知道"这功能会碰到什么"），GATE 0 重点让他看这张。

### ⑦ 控件规格表（→ 呈现断言；页面地图的对偶面）

| ID | page_ref | 元素含义 | 类型 | 情境 | 前置交互 | 文案字面值 | 状态 | 规则回指 | 来源 | 置信度 |
|---|---|---|---|---|---|---|---|---|---|---|

**这张表和 `page_map` 是同一批元素的两个侧面**：地图管「**在哪找它**」（selector），
表⑦ 管「**它该是什么样**」（文案 / 可见 / 可用 / 随情境怎么变）。

| 列 | 取值 | 说明 |
|---|---|---|
| `page_ref` | `page_map/<模块>/<页>.yaml: <element_key>` | **外键**，格式与 cases.md 的 `page_ref` 列一致。地图里还没有该元素 → 填 `⚠️待探索`，并进「已识别的依赖」段 |
| `元素含义` | 人能看懂的名字 | **不许填等于文案的废话**。反例见下「同名不同义」 |
| `类型` | `动作` / `导航` / `输入` / `展示` / `提示` | 决定 `exec` 分流（见「生成映射」） |
| `情境` | `维度=值` 组合，缺省写 `*` | 受控维度见下，不许自由造句 |
| `文案字面值` | 引号原文，逐字抄 | 权威源＝**设计图**（表现类）。看不出的标 `⚠️待实测` |
| `前置交互` | `—` / `hover:<元素>` / `click:<元素>` / `expand:<元素>`，可用 `→` 串联 | **要先做什么这个元素才出现。** 与地图的动力学字段对账 |
| `状态` | `✓可用` / `⊘置灰` / `✗隐藏` / `—不适用` | **三态而非布尔**——"看不见"和"看得见但点不了"是两种不同缺陷 |
| `规则回指` | 表④ 行 ID，如 `R07`；无对应规则填 `—` | **必填列**。它是防止表④/表⑦ 漂移的唯一机制 |

**`情境` 的受控维度（不许自由造句）**：

| 维度 | 取值来源 | 例 |
|---|---|---|
| `status` | 表③ 的状态枚举 | `status=待审批` |
| `role` | 表① 的「涉及角色」枚举 | `role=普通成员` |
| `step` | 流程第几步 / 是否末步 | `step=last` |
| `data` | `empty`（空态）/ `has_data` | `data=empty` |
| `time` | 时间边界 | `time=超出撤回期` |
| **横切维度**（可选） | 产品若有**租户 / 地区 / 语言**这类横切维度才启用；取值来自该维度的枚举。**没有就删掉这一维**，不要为了凑格式硬造 | `locale=en-US` |

**缺省 + 例外的写法（决策表思路，防止表爆炸）**：一个元素**通常只有 1 行**（`情境=*`），
**只为「规格与缺省不同」的情境加行**：

```
⑦-C07 | page_map/ticket/detail.yaml: btn_withdraw | 撤回本工单 | 动作 | *                             | —                   | "撤回"     | ✓可用 | —   | 设计图 | ✅确定
⑦-C08 | page_map/ticket/detail.yaml: btn_withdraw | 同上       | 动作 | status=已审批; time=超出撤回期 | —                   | "撤回"     | ✗隐藏 | R31 | 需求 3.4 | ✅确定
⑦-C09 | page_map/ticket/list.yaml: menu_close     | 关闭工单   | 动作 | status=待处理                 | hover:行→click:更多 | "关闭工单" | ✓可用 | R33 | 实测 | ✅确定
```

**禁止做全组合枚举**——「6 状态 × 3 角色 × N 个租户」的笛卡尔积没人审得了。

#### 五条硬纪律

1. **禁止写 selector。** 那是 `page_map` 的唯一职责，写进表⑦ 就是第二个真相。
   表⑦ 只声明「该有这个元素、该长这样」，**怎么找它由 page-map-sync 实地探索取证**。
   （这也让「先猜一份骨架地图」这个想法作废：它的价值被表⑦ 覆盖了，风险——猜 selector——被去掉了。）
2. **`规则回指` 必填。** 表④ 与表⑦ 是**分工不是复制**：表④ 只写判定（"有未结算子工单时不允许
   关闭"），表⑦ 只写呈现（"`关闭工单` 此时 ⊘置灰、Hover 显示那句话"），**两边内容零交集**，
   靠回指连起来。一旦两边都写了"不允许关闭"，那就是复制，必然漂移。
3. **每个 `⊘置灰` 行必须触发「锁定守卫」扫描**（见表④ 的「必做扫描」段）：
   写下"此时置灰"只回答了"现在能不能改"，还欠两个问题——**锁在什么条件下释放**、
   **锁解开后改了值、用旧值产生的存量数据怎么算**。这两行落在表④，不落在这里。
4. **`前置交互` 必填，直接可见的填 `—`。** 现代 SaaS 界面里"先 hover 出行尾三点图标 → 点开
   浮层菜单"、"先点按钮开抽屉"、"先展开折叠区"到处都是。**漏填的后果是生成的用例直接去点一个
   还没出现的元素。** 这一列与地图的动力学字段（`kind` / `gates` / `flows.steps`，以及地图
   description 里写明"需先 hover/展开/进入某步才出现"的元素）是同一批信息，**可双向对账**：
   地图说该元素要先 hover 才出现、而表⑦ 填了 `—` 的，必有一方错。
5. **同名不同义必须靠 `元素含义` 分开。** 典型坑：成员列表页的「状态」列＝**账号启用/停用**，
   订阅管理页的「状态」列＝**订阅套餐是否生效**，两者文案字面值完全相同、语义毫无关系。
   靠不同的 `page_ref` ＋ 说清差别的 `元素含义` 区分；`元素含义` 填"状态"等于没填。

#### 与表②/表④ 的边界（撞车高发区）

| 内容 | 归哪张表 | 理由 |
|---|---|---|
| 字段的必填 / 取值范围 / 默认值 | **表②** | 数据契约，与情境无关 |
| 字段的校验规则 ＋ 报错文案 | **表②** | 与校验规则同生共死，拆开会割裂；**表⑦ 不重复收录** |
| 字段「有 X 时锁定置灰」 | **表⑦** | 这是呈现，且依赖情境 —— 表② 里此类表述一律迁到表⑦，表② 只留数据契约 |
| "不允许删除" / "硬拦截不许提交" / "可用额度怎么算" | **表④** | 系统的判定结果 |
| "删除 ⊘置灰" / "Hover 显示某句话" / "该按钮此状态隐藏" | **表⑦** | 用户眼睛看到的形态 |

一句话判据**唯一出处在系统提示**（`.claude/agents/test-case-design.md`
「阶段1 关键纪律」段）。本表是它的展开，改判据要改那一处。

#### 双向对账（表⑦ 独有的能力）

| 方向 | 含义 | 处置 |
|---|---|---|
| 表⑦ 有 → 地图没有 | 该元素还没探过 | `page_ref` 标 `⚠️待探索`，进「已识别的依赖」，**表⑦ 就是给 page-map-sync 的探索清单** |
| **地图有 → 表⑦ 没有** | **该元素没有任何规格，无人守** | 算进控件覆盖率缺口；本轮不管的显式写进「未覆盖说明」 |

于是多出一个覆盖率指标：**控件覆盖率 = 表⑦ 覆盖的 `page_ref` 数 ÷ 地图该页 `elements` 总数**。
这是唯一能对**控件层**回答"我守了几个"的指标——没有表⑦ 就没有这个维度，
控件的可见性/可用性缺陷只能靠"碰巧写到了"来覆盖。

## 二、三种项目情况：怎么把这 7 张表填出来

**判断输入档位**（阶段1 第一件事，结论写进 decomp.md frontmatter 的 `input_tier`）：

| 档 | 输入现状 | 典型场景 |
|---|---|---|
| **A** | 有完整需求文档（含字段表/规则段/流程）±设计图 | 正式需求评审后的新功能 |
| **B** | 只有需求描述 / 变更单 / 用户故事 / 几张图 | **最常见**——小迭代、口头需求、需求变更 |
| **C** | 无需求文档，功能已上线 | 存量补测、探索式测试、回归池建设 |

同一个任务里不同表可以处在不同档（需求文档写全了字段但没写状态机 = 表② A 档、表③ B 档），
**按表分别标注**，不要笼统给整个任务打一个档。

### A 档：有完整需求文档

| 表 | 主要来源 | 典型缺口（必然要标 ⚠️ 的） |
|---|---|---|
| ① | 需求文档功能章节，每个"用户可以…"句 = 一个功能点 | 权限矩阵（哪些角色不能做）通常缺 |
| ② | 需求文档字段表直抄 | **空值行为、长度上界、报错文案、字段间依赖**——需求几乎从不写 |
| ③ | 需求文档状态清单 → 自己补成 N×N 矩阵 | 非法迁移格子 100% 是 `⚠️未定义` |
| ④ | 需求文档「限制/约束」段逐句抽 | 规则冲突时的优先级、边界归属（`≤` 还是 `<`） |
| ⑤ | 设计图 + 需求文档流程图 | **入口路径**（设计图只画新模块，不画怎么进来）、中断/回退路径 |
| ⑥ | 无 → 全靠三条 grep 线自挖 | 整张表 |
| ⑦ | **设计图逐屏盘点**（需求文档几乎从不写控件矩阵） | `page_ref` 全是 `⚠️待探索`（UI 未提测）；`状态`/角色差异大量 `⚠️缺失` |

**A 档的活不是"抄需求文档"，是"抄完之后把需求结构性不写的四块补成 ⚠️ 行"**：空值行为、非法
迁移、报错文案、影响面。抄需求那部分 20 分钟，这四块才是解构层的产出。

### B 档：需求描述 / 变更单（最常见）

顺序：先立①，再用**类比**填 ②③④，⑤靠图，⑥照挖。

1. **①功能点**：从 UI 设计图/原型反推（每个新增控件区 = 候选功能点）；没有图就从用户故事的
   动词反推。产出后**在 GATE 0 首先让用户确认范围**——B 档最大的风险是范围本身错了。
2. **②③④ 用类比填**：项目里已有的同类功能是默认模板。
   - 同名/同义字段查项目知识库和 `page_map/**` → 抄它的约束，标 `🔶推断` + 写明类比对象
   - 同类实体的状态机查项目知识库里已有的状态流转说明
   - 平台默认约定查 `CLAUDE.md` / 项目约定
   - **类比不到的一律 `⚠️缺失`，不许拿"常识"顶**
3. **⑤旅程**：有图按图，无图只写到"入口 + 主干动作"，细节整段标 `⚠️缺失`，
   在 decomp.md 里显式声明「本旅程需提测后实测补全」。
4. **⑥影响面**：跟 A 档一样挖，B 档反而更重要——小改动最容易碰坏存量。
5. **⑦控件规格**：有设计图就逐屏盘；没有图则**只填已存在于地图的元素**（类比同类页面的
   可见/可用规则，标 `🔶推断`），新元素整段标 `⚠️缺失`，不许凭想象造控件清单。

**B 档的 GATE 0 是整条链路上性价比最高的一次人机交互**：满屏 `🔶推断`，用户扫一遍表格，
认同的不动、不对的直接改 cell。这比让他读一份几十条的 cases.md 判断"够不够"便宜一个量级。

### C 档：无需求文档（存量功能补测）

**填表顺序反过来：⑤ → ② → ③ → ④ → ① → ⑥**，因为唯一的真相源是运行中的系统。

1. **前置**：orchestrator 必须先派 `page-map-sync` 实地探索（C 档没有这一步就无法解构）。
   事实来源是 sync.md 的「行为实测记录」一节（字段约束 / 校验文案 / 状态与可点动作）和 page_map。
   解构者自己**不上网站**；缺哪类证据，就列进「已识别的依赖」，由 orchestrator 再派一次 page-map-sync 补采。
2. **⑤旅程**：实地走一遍主流程，来源 = `实测`，置信度 = `✅确定`（实测是最强证据）。
3. **②字段**：从 DOM 抓 `required` / `maxlength` / `pattern` / 下拉枚举值 / 默认值 /
   placeholder；报错文案靠**主动触发校验**取证。
4. **③状态机**：从 UI 上可见的状态标签枚举出状态集合，从各状态下**可点的动作按钮**推出合法
   迁移；不可点/不出现的按钮 = `🚫禁止`（有实测证据的禁止，比文档写的还硬）。
5. **④规则**：把 ②③ 触发校验时看到的拦截行为反写成规则。
6. **①功能点 / ⑥影响面**：最后汇总归类。
7. **⑦控件规格**：C 档是表⑦ **最容易填的一档**——地图已实测，直接**以该页 `elements` 为全集
   反填**，逐个元素记 `文案字面值` / `状态` / 角色差异，来源＝`实测`。这一档的控件覆盖率
   天然接近 100%，也是唯一能一次性把某个页面的控件规格盘清的机会。
8. **C 档必须同时回写项目知识库** ——这往往是该模块唯一一次系统性盘点，不回写等于白做
   （回写动作见下「四、迭代闭环」）。

> C 档的 decomp.md 置信度整体高于 A/B 档（实测 > 文档），但**覆盖的是"系统现在是什么样"，
> 不是"系统应该是什么样"**。所以 C 档的 GATE 0 必须额外问用户一句：表里哪些实测行为是
> **合理的**、哪些其实是**存量 bug**——agent 分不出来，用户能。

## 三、生成映射（阶段2 机械执行，不许自由裁量）

confirmed 的 decomp.md → cases.md 是**查表**，不是"再想想"：

| 素材表 | 测试设计方法 | 产出用例形态 | 数量下界 |
|---|---|---|---|
| ① 功能点 | 骨架 / 优先级分配 | 每个功能点 ≥1 条正向主流程 | = 功能点数 |
| ② 字段规格 | 等价类 + 边界值 | 必填 → 空值 1 条；有 min/max → 边界 2~4 条；枚举 → 每值 1 条（值多时按等价类合并）；有依赖 → 依赖组合 1 条 | 按上述规则逐字段累加 |
| ③ 状态机 | 状态转换法 | 每条 `✅合法` 迁移 1 条；`🚫禁止` 格子按「同角色不可达」「跨角色越权」两类各抽样 | = 合法迁移数 + 非法抽样数 |
| ④ 业务规则 | 决策表 | 条件组合列判定表，化简后每列 1 条 | ≥ 规则数 |
| ⑤ 操作旅程 | 场景法 | 每旅程 1 条端到端 + 有回退设计的加 1 条中断/回退 | = 旅程数 |
| ⑥ 影响面 | 回归选择 | 每条 `依赖`/`冲突` 关系 1 条回归断言；已有用例能覆盖的标 `reuse: <路径>` 不重复写 | = 依赖+冲突关系数 |
| ⑦ 控件规格 | 呈现断言（决策表变体） | **按「屏 × 情境」聚合**：每个去重后的情境 1 条用例，断言该屏**全部**元素的 `状态` 与 `文案字面值` | = **去重后的情境数**，不是元素数 |

> **⑦ 的聚合是硬要求，不是优化。** 一个元素一条用例会炸：一张 6 状态 × 8 控件的呈现矩阵，
> 逐元素写就是 48 条，按情境聚合是 **6 条**——每条的期望就是矩阵的一整行。这个粒度恰好等于
> 人手测时的动作：**进到某状态，扫一眼这屏该有什么、不该有什么。**
>
> **`exec` 分流按 `类型` 列**：`动作`/`导航`/`输入` → `auto`（错了有功能后果）；
> `提示`/`展示` 且无功能后果 → `manual`（逐条断言装饰文案，UI 一微调就红一片，维护成本会反噬）。

**优先级由映射决定，不凭感觉**：

- `P0` = ①的正向 + ⑤的主旅程（挂了就是主流程断了）
- `P1` = ②的边界 + ③的合法迁移 + ④的规则
- `P2` = ③的非法迁移/越权 + ②的异常输入 + ⑥的回归 + **⑦的纯文案断言**
- **⑦ 的可见性/可用性差异归 `P1`**——尤其跨角色的：某按钮本该对普通成员隐藏却可见，
  是权限缺陷而非显示瑕疵

**回指与对账（硬校验）**：

- cases.md 每条用例必带 `derived_from` 列，格式 `②-F07` / `③-S03` / `④-R02`（表号-行ID）
- **反向对账**：7 表每一行都要在 cases.md 的某条 `derived_from` 里出现过；没出现的必须进
  cases.md 的「未覆盖说明」段并写理由（合法理由只有两类：
  ① 本轮不改动且已有用例覆盖，附路径；② 该行是 `⚠️缺失`，待实测后补）
- `⚠️缺失` 的行**照样要生成用例**——生成的是 flow.md 里的 `⚠️待实测` 项，交给提测后取证，
  不是跳过

## 四、迭代闭环：⚠️ 的生命周期 + 回写知识库

每个 `⚠️` / `🔶` 都必须走完这条路，不许在中途蒸发：

```
decomp.md 标 ⚠️/🔶
      │
      ├─ GATE 0：用户当场能答的 → 直接改 cell，来源=`用户`，置信度=✅
      │
      └─ 答不了的 → 阶段2 落成 flow.md 的 ⚠️待实测 项
                          │
                    提测后 page-map-sync 取证 / test-writing 自跑
                          │
                    ops_review.md 裁决（实际：… / 产品bug：…）
                          │
                    ★ 收口：回写项目知识库（如 specs/<module>/*.md）★
                          │
                下一迭代解构同模块时，知识库成为表②③④的第一输入源
                → 该项在新的 decomp.md 里直接是 ✅确定
```

**收口是强制动作，不是"最好做一下"。** 没有回写知识库，这套方法论就只是"每次都认真做一遍"，
不是"每次都比上次省力"。具体协议：

- decomp.md 里每个 `⚠️缺失` / `🔶推断` 行分配一个**解构债 ID**：`DBT-001`、`DBT-002`…
  并在 decomp.md 末尾维护「解构债清单」段（ID / 所属表 / 描述 / 问题 / 背景 / 选项 / 状态 `open|answered|verified`）
- **［需判断］和 ⚠️冲突 的债必须填「问题 / 背景 / 选项」三列**——这三列会原样出现在评审人面前（见下）

### 写给评审人的三列：问题 / 背景 / 选项

「描述」列是写给 agent 自己和下游对账用的，可以用速记；**「问题 / 背景 / 选项」是写给评审人的**，
评审控制台直接拿它们当决策卡的标题、说明和按钮。评审人往往没读过需求、没看过解构表，
卡片上的字必须**单独拿出来就能看懂、看完就能作答**。

| 列 | 怎么写 | 反例 → 正例 |
|---|---|---|
| **问题** | 一句完整问句，问**一个**决定；用产品语言，不出现表号 / 行号 / DBT / 「正文 vs 变更日志」这类内部速记 | ❌ 冲突：正文 §3.2「昵称均改为选填」vs 变更日志 2026-05-12「企业账号必填」；以及该规则是否对 App 和网页端都生效 → ✅ 企业账号的昵称是必填还是选填？ |
| **背景** | 两三句话：为什么要问、两边各怎么说 / 缺了什么、答案会影响什么。引用原文处按「来源」列的可定位格式写（`需求 §2.2` / `变更日志 2026-09-28` / `设计图 img_04`），控制台会把原文贴在背景下面 | ✅ 需求 §3.2 说注册页的昵称改为选填；变更日志 2026-05-12 补了一条：企业账号注册时昵称必填。两处冲突，用例按哪条写？ |
| **选项** | 用「；」分隔的**具体答案**，每项写出"选了之后规则是什么"；你的工作假设那项末尾加 `（默认）`。**不写「是 / 否」**，除非问题本身就是单一是非题；「我来说明」「留给提测」两个兜底项控制台自动补，不用写 | ❌ 是；不是 → ✅ 以变更日志为准：企业账号昵称必填，个人账号选填（默认）；以需求 §3.2 为准：所有账号昵称都选填 |

**一卡一问**：一条债只问一个决定。一个冲突里同时藏着「按哪条」和「适用范围」两个问题时，
**拆成两条债**（各自引用同一表行即可）——两个问题塞进一张卡，评审人就只能选一个答案回答两件事。
［可提测］的债三列可填 `—`（它们默认不进评审队列）。

### 会被人读到的文字：不许用代号指代别的条目

评审控制台会把决策卡涉及的表格行原样贴出来当证据，评审人**看不懂内部编号**。所以表格里的列分两类：

| 列的类别 | 包括 | 能不能写 `R02` / `F07` / `A01–A04` / `S1` / `DBT-003` / `表④` 这类代号 |
|---|---|---|
| **编号与回指列**（给 agent 对账用） | `ID`、`债ID`、`所属表`、`所属功能点`、`规则回指`、`涉及字段`、`page_ref`、`置信度` | 可以，这就是它们的用途 |
| **人读列**（其余所有列） | 功能点、字段、条件、结果/约束、取值/约束、校验规则、旅程、步骤、预期、元素含义、情境、状态、来源、问题、背景、选项…… | **不可以** |

人读列里需要提到另一条内容时，二选一：

1. **用一句话把它说出来**：❌ `R02 的必填规则在哪几个端生效未写明` → ✅ `"企业账号昵称必填"这条规则在 App 和网页端是否都生效，需求没写`
2. **指向需求原文的位置**，让人自己去看：✅ `见需求 §2.2（第 20 行）`、`见变更日志 2026-09-28（第 46 行）`

状态机也一样：状态写名字，不写编号（❌ `S1 已提交` → ✅ `已提交待审核`）；功能点范围写清是哪些（❌ `A01–A04` → ✅ `新增、编辑、删除、查看这四个入口`）。

**`DBT-xxx` 编号**是控制台把表格行归到决策卡的依据，不能删，但要放在该行的「置信度」列里；只有没有
「置信度」列的矩阵类表（如状态机 N×N 总览），才允许写在格子里（控制台显示时会自动去掉）。

**交付前机器自检**：`python3 tools/gate_review.py parse <task_id>` 会列出人读列里残留的代号，**必须为 0**。
- GATE 0 用户答复的 → 标 `answered`
- 提测后实测取证的 → test-writing 阶段2 在 `impl.md` 的「解构债结算」段列出
  `DBT-00x → 实测结论 → 应回写知识库哪个文件的哪一节`
- **orchestrator 在任务终态前必须检查**：impl.md 有「解构债结算」段，且结算条目已回写知识库；
  未结算的债在 `state.md` 终态原因里列出（允许挂账，不允许静默丢失）

### 需求版本锚定：入档 + frontmatter

**有需求文档就必须入档**：需求文档与设计图一律复制到 `artifacts/<task_id>/input/` 与
`artifacts/<task_id>/ui_design/`，**agent 从入档目录读，不从派发 prompt 的正文读**。
派生产物 frontmatter 的 `prd_version` 指向入档文件里的版本标识。

> **入档不是仪式，是版本锚。** 你后来又拿到新版需求时，`input/` 里有几份一目了然，
> 而不是靠回忆"上次贴的是哪版"。prompt 正文里若也贴了需求，**以入档文件为准**，
> 并在 artifact 里记一句不一致。

**走 B/C 档、本来就没有需求文档时**，不是拒绝执行，而是**显式声明缺口**：
frontmatter 写 `prd_version: none (tier C)`（或 `none (tier B)`），
并在正文「输入档位判定」段写清楚"本轮无需求文档，真相源是 XXX"。
**唯一不可接受的是空着或编一个版本号。**

**为什么版本号这么要紧**：需求是会改的，下一轮拿新版重解构时，「上一轮说 X，这轮说 Y」
有三种可能：①上轮漏了 ②新版需求改了 ③需求范围变了。**没有版本号就分不清**，
会把"产品已修正"误判成"我们上次漏了"，白白重查一遍。
同模块有上一份 decomp.md 的，`baseline_decomp` 填它的路径。

**这套东西的收敛形态**：同一模块跑到第 3~4 个迭代时，表②③④ 应该基本全是
`✅确定 / 来源: 知识库`，解构层退化成"读知识库 + 只解构本次变更"，耗时从小时级降到分钟级。
**如果第 3 个迭代解构还是满屏 ⚠️，说明回写知识库这一步没真做**——这是这套方法论唯一的健康指标。

## 五、decomp.md schema

> **格式的唯一出处是模板** `artifacts/templates/decomp.template.md`：阶段1 起手先 `cp` 它，再往里填，不要凭下面这段说明重新搭表头。
> 评审控制台和 `python3 tools/gate_review.py check <task_id>` 都按模板的列名核对；frontmatter 的 `contract` 字段标明本清单按哪一版契约写的
> （当前 v2：解构债清单带「问题 / 背景 / 选项」、人读列不用代号；改了卡片依赖的格式就升版本号）。


## 六、阶段1 红线

**唯一出处在系统提示** `.claude/agents/test-case-design.md` 的「红线」段——本文件不复制。

同一条规则写两份必然漂移：改了一边忘另一边，就有了第二个真相，而两个真相里没人知道
哪个是对的。**新禁令一律只加到系统提示**（agent 无条件读得到），本文件只负责展开方法论
（怎么填、为什么这么填），不负责重申禁令。
